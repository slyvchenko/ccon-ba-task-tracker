# PR #60: перевірки узгодженості SQLite після аварійного завершення (v2.50.1)

## Що посилено

- `Desk.connect()` явно встановлює `PRAGMA synchronous=FULL` на кожному з'єднанні. Це звичайний SQLite commit-durability режим. Синтетичні тести підтверджують значення PRAGMA; **реальну гарантію проти втрати живлення на конкретному SSD/Windows** ці тести не встановлюють.
- Backup перед публікацією синхронізує завершену SQLite-копію й metadata JSON. Придатність до restore настає **лише після** публікації останнього `.json`-маніфесту. На POSIX після атомарного перейменування синхронізується directory entry; на Windows portable Python не надає еквівалент fsync директорії, отже потрібне Windows UAT.
- Offline restore перевіряє фінальну тимчасову базу, синхронізує її перед атомарною заміною. Попереднє обов'язкове створення rescue backup, серверний лок і відмова за наявності WAL/SHM залишилися без змін.

## Синтетичний crash drill

`tests/test_crash_consistency.py` запускає **окремий процес на тимчасовій базі** та припиняє його:

1. Після SQL UPDATE, але до запису history/COMMIT: відновлення журналу SQLite після restart має зберегти попередню підтверджену нотатку, email draft, статус, revision, import count та історію.
2. Посеред транзакції імпорту багатозадачного snapshot: жодна нова задача чи metadata не повинна стати видимою після restart.
3. **Після** повернення підтвердження `manualRevision`: попри негайне аварійне завершення процесу нова нотатка, draft, revision і history повинні залишитися в SQLite.
4. Після публікації файлу backup, але до маніфесту: такий orphaned SQLite файл **не** допускається до restore, існуючі підтверджені backup не втрачаються, наступний backup успішний.
5. Помилка перед останньою атомарною заміною offline restore: поточна база і зміни залишаються незмінними, приватний `.pending` не залишаються без очищення.

Усе виконується на синтетичному SQLite, без корпоративного Jira/CCON/Kibana, фактичного вимкнення живлення, токенів, користувацьких документів або браузерних даних. Тести не виконують доступу до реальної користувацької БД. На Windows subprocess terminate/SQLite rollback перевіряється CI окремо.

## Що ще НЕ прийнято

- **REL-02 P0:** реальний browser multi-tab/recovered localStorage + примусове закриття Windows, кінцеве підтвердження користувачем.
- **REL-03 P0:** Windows filesystem/SSD/BitLocker/ACL/backup policy та ручний restore реальної інсталяції.
- **REL-05 P1:** вимкнення живлення, Windows Task Scheduler/service restart, locked DB/антивірус/довгі імпорти на справжній машині.
- Синтетичний CI не підтверджує фізичний hardware write-cache/barriers і не замінює 8-годинний soak чи 26 BA gold-кейсів. Усі `human_acceptance` у канонічному ledger залишаються `NOT_RECORDED`.

**Важливо:** не запускайте аварійні subprocess-тести проти особистої або корпоративної бази. Для реального відновлення діє `docs/PRIVATE_BACKUP_RESTORE.md` із офлайн-кроками та ручною перевіркою.
