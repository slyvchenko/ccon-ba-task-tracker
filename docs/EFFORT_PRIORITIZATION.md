# PR #29: оцінка тривалості та підказки швидких дій без зміни офіційних пріоритетів

**Статус:** реалізовано в коді v2.29, **не** перевірено на реальному Windows/BA gold-case наборі. Власник: один BA. Особисті ручні оцінки, Jira та постачальники не синхронізуються між собою.

## Контракт пріоритетів

Трудомісткість **не є** компонентою queueScore та **не змінює** `rankTasks`. Безумовний порядок залишається: підтверджений активний спринт перед backlog; реальна потреба WRITE перед READY / DECIDE / REVIEW / WAIT в кожній групі; далі існуючі action rank, score 0–100, ознака блокування й порядок snapshot. Ручний DONE та WAIT мають свій чинний стан. Оцінка часу не здатна «просунути» невідому, просту, застарілу чи заблоковану задачу.

**Стандартний екран збережено:** у звичній картці з'являється короткий розрахунок обсягу, причина й джерело; ручна оцінка задається у вже існуючому блоці «Мій робочий стан» та зберігається разом із нотаткою. Маленький індикатор `S?` у списку є лише підказкою «перевір можливу коротку дію». Він **не пересортовує** чергу, не створює Quick Mode, не маркує вимоги як business-correct, не позначає DONE й нічого не надсилає.

## Значення та джерела

| Band | Орієнтир | Приклад робочої гіпотези |
|---|---|---|
| XS | До 2 хв | Дрібний підтверджений ручний крок (лише вибір BA) |
| S | 2–5 хв | Є перевірена за структурою чернетка та зрозуміла наступна дія |
| M | 5–20 хв | Непідготовлений лист або декілька перевірок |
| L | 20–60 хв | Потрібне рішення, перевірка RCA, кілька невизначених правил |
| XL | Понад 60 хв | Багато правил, джерел або невирішених умов |
| UNKNOWN | Не оцінено | Застаріла задача, немає актуального аналізу, WAIT, DONE або немає структури для навіть грубої оцінки |

Показники не є виміряною тривалістю та не гарантують завершення. Не використовуйте їх для автоматичного погодинного планування чи бонусів без людської калібрації.

| Source | Що означає | Confidence |
|---|---|---|
| `MANUAL` | BA явно встановив XS/S/M/L/XL, зберіг у SQLite, може змінити в будь-який момент | `USER_SELECTED`, лише власна оцінка людини, не замір |
| `HEURISTIC` | Суто детерміноване попередження за поточними структурованими полями: сигнал, доказова готовність, кількість правил/прогалин, підготовленість листа | `LOW`, непідтверджена гіпотеза |
| `UNKNOWN` | Немає припустимої оцінки; ручне скидання повертає до евристики, яка також може сказати UNKNOWN | Невідомо |

**Не виводимо час із назв постачальників, PNR, вмісту приватних REST/XML, «AI думає, що це просто» або обсягу тексту**. Технічна складність залежить від реальної інтеграції, доступності supplier response, QA й неоднозначності бізнес-правил.

## Логіка рекомендації

1. Немає актуального (відносно fingerprint) аналізу, задачі немає в активному списку, вона в DONE/WAIT → UNKNOWN.
2. Правил 8+ або відкритих питань 6+ → XL.
3. REVIEW, DECIDE, quality gate BLOCKED, питань 3+ або правил 4+ → L.
4. Quality Gate не `STRUCTURALLY_VERIFIED` → UNKNOWN.
5. Хоч одне незакрите питання, правила 2+ або шість джерел → M.
6. WRITE зі сформованими адресатом, темою і body → S (але сам email і всі ZIP перевіряє BA). WRITE без одного з них → M.
7. READY із підготовленою структурно перевіреною чернеткою → S.
8. Усі інші ситуації → M або UNKNOWN залежно від наявності доказів.

**Порядок правил зупиняється при першій відповідності**. Жодна евристика не автоматизує Done і не змінює Jira.

## Quick-win candidate ≠ пріоритет

Підказка показується **тільки** коли XS або S, актуальний аналіз, активна незавершена задача, сигнал READY/WRITE, `qualityGate.state=STRUCTURALLY_VERIFIED`, і немає відкритих питань у `analysis.missingInfo` чи `briefing.unknownsUk`.

Рекомендації зберігають **індекс у звичайній відсортованій черзі**. Навіть задача з ручним XS на backlog **не піднімається** над READY/WRITE із підтвердженого спринту або над задачею з вищим балом, blocking чи рангом дії. Неможливо використати значення effort для обходу hard constraints.

**Приклад:** у sprint є BA-інцидент на 60 хв (високий score), а в backlog є лист на 2 хв (XS). Лист залишається поза sprint нижче. У списку видно можливий короткий крок, але вибір часу/відволікання ухвалює аналітик.

## Data lifecycle і приватність

- Міграція SQLite: `tasks.manual_effort TEXT NOT NULL DEFAULT 'UNKNOWN'`. Ручна оцінка не перезаписує ні note, ні draft, ні manual_status; reset на UNKNOWN повертає до підказки.
- `GET /api/tasks` додає `manualEffort`; `POST /api/tasks/CCON-...` приймає тільки ENUM, атомарно записує разом із CAS `expectedManualRevision`. Stale tab → 409; жодна зміна не губиться тихо.
- Після нового Jira snapshot ручна оцінка зберігається, як і особисті чернетки. Якщо контекст змінився, **візуалізація не вдає**, що аналіз залишається актуальним. Аналітик може переглянути раніше встановлений effort.
- Відновлення unsaved form відбувається в наявному приватному browser storage з pinned manualRevision. Жодної телеметрії або реальних кейсів у CI.
- Звичайні saveStatus та legacy API-виклики, які не несуть `manualEffort`, **не перезаписують** збережену оцінку. Старий SQLite schema міг бути без колонки: міграція суто адитивна.
- Загальне обмеження v2.27 лишається: legacy зовнішні POST без CAS токена не захищені від конфлікту. Новий інтерфейс завжди використовує CAS.

## Перевірки і критерії завершення

**Автоматичні в PR #29:**
- Node: всі bands та source-confidence; stale/WAIT/DONE/archive; готовий / непідготовлений WRITE; blocked proof; підтвердження unknown; сотні комбінацій status, sprint, signal, score проти **байт-в-байт того самого порядку** rankTasks; немодифікація вхідної задачі.
- Python: round-trip XS→UNKNOWN та restart; старий SQLite; snapshot; невалідні значення; email/status збережені; two-tab CAS.
- Offline package: новий JS module в static allowlist і manifest; жодного додаткового Python пакета.

**Реальний UX UAT перед визнанням вигоди:** на 20–30 задачах, що вже переглянуті незалежним BA, зафіксувати band до виконання та фактичний час; порахувати точність ручних та евристичних band, частку розбіжностей більше 1 band, якість вибору quick wins, rework/false-ready і відволікання від blocking work. Окремо Windows/Chrome/Edge перевірити клавіатурне Save/Next, дві вкладки, відновлення й прокрутку. Не заявляти, що трудомісткість передбачена точно чи що швидкість роботи зросла без таких даних.
