# v2.32: приватне резервування, перевірка й офлайн-відновлення CCON BA Desk

**Власник:** локальний BA. **Статус:** реалізовані код і синтетичні тести; повний Windows crash/restore UAT відкритий. Цей механізм не відправляє файли у GitHub, Jira, пошту, хмарне сховище або інші зовнішні сервіси.

## Дані, які захищаються

- Повна SQLite `ba_state.db`: поточні Jira snapshot-метадані, ручні статуси, оцінки XS–XL, нотатки, **збережені** чернетки листів, history, CAS `manualRevision`, ревізія snapshot і журнал імпортів. Нічого з цього не експортується в CI.
- **Не входять у DB backup:** незбережений текст у localStorage браузера, `inbox/`, Jira context JSON, supplier ZIP/XML, завантаження й інші файли `data/`. Для них потрібна окрема безпечна стратегія резервування, а не припущення, що backup DB вже зберіг усе.
- Папка `backups/` вже є у `.gitignore`, не є HTTP static route й не включається в release ZIP. Копії містять **конфіденційні дані**, зберігаються **незашифрованими SQLite-файлами**. На Unix встановлюються локальні дозволи 0700 (папка)/0600 (файл). На Windows доступ залежить від ACL папки облікового запису: використовуйте BitLocker/корпоративне шифрування диска, не розміщуйте backups у загальнодоступних папках чи синхронізації.
- JSON metadata поруч із копією містить лише версію формату, ім'я файлу, UTC час, SHA-256, розмір, кількість задач і число ревізії. Ніяких PNR, описів, листів, нотаток, корпоративних URL чи ключів доступу.

## Автоматичний цикл

На старті локального `server.py`, **перед міграцією старої бази**, перевіряється наявність перевіреної резервної копії за попередні 24 години. Якщо такої немає й SQLite DB існує, виконується **SQLite online backup API** до приватного тимчасового файлу, PRAGMA integrity_check, перевірка схеми, обчислення SHA-256 та атомарна публікація `.sqlite3` + `.json`. На новій інсталяції копія створюється після створення бази/першого імпорту. Поки застосунок відкритий, контроль відбувається раз на 5 хвилин та робить нову копію лише після закінчення 24-годинного інтервалу.

Зберігається до **семи останніх успішно підтверджених копій**. Під час неуспішного резервування попередні копії не стираються; локальний статус «Дані» показує помилку. При проблемі на старті, коли захистити вже наявну базу не вдалося, новий сервер **не запускається мовчки з міграцією**. Якщо сервер уже працює, нові спроби резервування здійснюються онлайн без зупинення користувача.

Період резервування **не гарантує нуль втрат** правок після останньої копії (RPO до ~24 годин у нормальному режимі; довше при помилках backup). Перед критичними змінами запустіть ручне резервування. Відновлення не підміняє регулярний захищений offsite backup.

## Ручні команди (Windows PowerShell / у папці застосунку)

```powershell
py -3 local_backup.py status
py -3 local_backup.py backup
# Скопіюй filename зі списку приватних файлів backups/:
py -3 local_backup.py verify --name backup-YYYYMMDDTHHMMSSZ-XXXXXXXXXXXX.sqlite3
```

Для **відновлення з попередньої версії**:

1. У всіх вкладках збережи власні правки; **закрий браузерні вкладки** CCON BA Desk. Незаписані локальні чернетки окремо збережи, інакше вони можуть залишитися з ревізією, що не відповідає відновленій базі.
2. **Зупини процес CCON BA Desk** у консолі або Windows Task Scheduler. Переконайся, що не запущено стару копію сервера чи зовнішні SQLite-конектори.
3. Перевір необхідний файл: `py -3 local_backup.py verify --name <filename>`. Усі файли повинні бути у приватній `backups/`; шлях `../` та симлінки заборонені.
4. Явно підтвердь офлайн-операцію:

```powershell
py -3 local_backup.py restore --name backup-YYYYMMDDTHHMMSSZ-XXXXXXXXXXXX.sqlite3 --confirm "RESTORE LOCAL BA DATA"
```

5. Перед заміною існуючої DB застосунок автоматично створює **додаткову перевірену rescue-копію**, перевіряє наявність незакритого SQLite WAL, створює відновлену базу в тимчасовому файлі SQLite Backup API, повторно перевіряє цілісність та лише тоді робить атомарну заміну `ba_state.db`. Якщо lock сервера зайнятий, хеш/схема **вхідної резервної копії** зламані, підтвердження відсутнє, залишились WAL/SHM-файли або **справну поточну DB** не вдалось зарезервувати, **поточна DB не замінюється**. Якщо **поточна DB пошкоджена**, онлайн-rescue може бути неможливим: перед відновленням створюється окремий сирий файл `backups/damaged-*.sqlite3` для форензичного аналізу; він **не є перевіреною резервною копією** і ніколи не пропонується для звичайного restore. Якщо поряд є WAL/SHM, операція зупиняється **до відкриття пошкодженої бази**; потрібна ручна офлайн-діагностика зі збереженням sidecar файлів.
6. Запусти `Start CCON BA.bat` або звичний розклад. Перевір ревізію, notes, drafts, history, статуси, один Save/Restart, реімпорт. **Не запускай застосунок на старій резервній базі разом із неоновленою вкладкою**, яка може намагатися повторно зберігати власний старий стан.

**Rollback:** якщо новий UI/схема працює некоректно, спершу зупини процес, створіть ручну резервну копію поточного стану, потім повтори offline restore попередньої копії. Не видаляй `ba_state.db` або `backups/` для «ремонту». Міграція SQLite адитивна; поведінку старих бінарних релізів слід окремо перевірити.

## Збої імпорту та статус операцій

- `SnapshotMonitor` перевіряє `mtime_ns + size`, пропускає успішно оброблений незмінений файл і повторює невдалу спробу не частіше ніж через 30 секунд; зміна файлу запускає перевірку одразу. Це зменшує CPU на довгих щоденних сесіях.
- `GET /api/health` віддає тільки вже авторизованим локальним клієнтам `localBackup` з `available/createdAt/revision/backupCheckFailed` та `snapshotWatcher` з `state/attempts/failures/lastSuccessAt/lastFailureAt`. Немає прямого GET файлу backup. У хмарному режимі `localBackup=null`.
- Звичне меню **Дані** показує стан копії та останнього watcher import **без повторного toast кожні 5 секунд**. Фоновий імпорт не видаляє ручні нотатки/drafts й не посилає відповіді Jira.
- Окремий локальний cross-process lock `.local-server/.pipeline.lock` утримується весь час роботи server і використовується офлайн-відновленням. У разі зайнятості restore зупиняється; після завершення `serve_forever` watcher отримує stop, socket закривається, watcher приєднується.

## Перевірки у CI й ручний UAT

**Автоматичні синтетичні:** `python -m unittest tests.test_local_backup -v` і `python check_project.py`: повний round-trip SQLite і rescue; SHA tamper; неправильне підтвердження; lock/refusal; симлінк/шлях; сім копій і retention; broken JSON; старий schema; watcher retry interval та виправлення файлу; статуси/notes/email/effort/history з CAS. Всі fixtures створюються у тимчасовому каталозі; жодних реальних Jira або листів.

**Відкрито в реальному Windows UAT:** kill сервер під час save/import/backup (у тестовому середовищі), emergency restore з двома вкладками, BitLocker/ACL, файлові блокування антивірусом, незавершені .pending файли після hard power-off, Windows Task Scheduler кілька інстансів, Chrome/Edge keyboard/screen reader/400% zoom, контроль відсутності втрати всіх **підтверджених до backup** правок. Зміна `main` в GitHub сама по собі не оновлює локальний Windows інсталятор чи Task Scheduler.

**Не автоматизовано у #32:** резервування інших `data/`/supplier ZIP, шифровані offsite копії, постійне відновлення браузерних незбережених чернеток і бізнес-коректність Jira/REST; залишаються окремими задачами.

**Обслуговування приватної папки:** файли `backup-*.pending`, які залишились після аварійного вимкнення понад 1 годину тому, прибираються при наступному backup; свіжі файли іншого процесу не чіпаються. Нові точки відновлення відбираються за фактичним UTC часом створення з мікросекундами, а не випадковим суфіксом у назві. Некоректний/необ’єктний JSON-маніфест і зламаний файл не вважаються валідною резервною копією та не блокують створення наступної.
