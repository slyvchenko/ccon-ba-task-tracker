# Фінальний технічний closeout BA Desk (v2.50.14)

Мета: **однією командою** отримати безпечну, детерміновану карту всіх 129 пунктів і побачити, що саме залишилося до незалежного приймання, а не множити нові PR для вже реалізованих функцій.

## Команди

```powershell
python backlog_audit.py --check
python release_readiness.py --closeout
python release_readiness.py --closeout --require-ready
```

Перша перевіряє відповідність канонічного реєстру його згенерованій копії. Друга **тільки читає** цей реєстр і виводить JSON з усіма ID, пріоритетами, статусами, ознаками наявності code/test-посилань, дією для приймання й незакритими зовнішніми gate. Ніяких приватних Jira/PNR, supplier XML/REST, листів, нотаток чи імен рецензентів у результаті немає. Код не викликає Jira/Kibana/CCON, не записує сховище й нічого не завантажує в мережу.

Третя команда навмисно завершується **exit code 2**, поки незалежний BA/Windows UAT не підтверджений. Вона не «розблокується» навіть якщо хтось вручну змінить `human_acceptance` у публічному JSON на `PASSED`.

## Що вже готово

- Усі 13 початкових `PLANNED` мають технічні реалізації та стали `PARTIAL`, а не автоматично `DONE`. В інвентарі **0 PLANNED**, **0 NEXT**.
- Усього 129 вимог: **40 IMPLEMENTED за кодом**, **82 PARTIAL**, **3 GATE**, **4 DEFERRED**. Для **109** є прямі посилання на код + тест; для **14** немає прямого code locator. Поле `sourceTestPointerCoverage` рахує **лише ті рядки, де одночасно присутні обидва вказівники**: на код і на тест. `pointerCoverageBreakdown` показує 109 з обома вказівниками, 6 лише з code locator, 0 лише з test locator і 14 без обох. `p0PointerGaps` містить тільки дозволені публічні ID і категорії P0-прогалин, без шляхів, змісту задач чи приватних даних. Це карта для аудиту, а не оцінка якості чи доказ відсутності коду. Покриття вказівниками не означає, що функція пройшла business UAT. Відсутність посилання не доводить відсутності реалізації.
- Чотири `INF-01..INF-04` відкладені як окремий хмарний продукт. Вони не є дозволом потай запускати cloud/SSO.
- Головне джерело рішень: `docs/PRODUCT_BACKLOG.md`. Детальний незакритий work plan: `docs/REMAINING_WORK_PLAN.md`, автоматичний ledger: `docs/BACKLOG_ACCEPTANCE_LEDGER.json`.

## Правило завершення

Стан `PARTIAL` не доводить, що потрібно написати ще 82 функції. Часто бракує реальної перевірки, доступу до джерел або ручного рішення щодо scope. Водночас сам code/test locator не є доказом бізнес-правильності. Без фактичних приватних кейсів, Windows-перевірок та незалежного рішення **releaseApproved=false** залишається єдиним коректним результатом.

**Наступна робота, що залежить від користувача:** на авторизованому комп'ютері виконати наведений протокол для 26 кейсів і Windows, зібрати докази в приватному сховищі, виписати конкретні знайдені дефекти, й лише тоді формувати змістовні виправлення. Issue #50 залишається відкритим.

## Уточнення: пріоритет P1 (код і тести, не бізнес-приймання)

Після перевірки 16 P1-вимог додано навігаційні code+test locator у детермінований реєстр. Вони фіксують, **де саме шукати** вже наявні алгоритми та синтетичні регресії. Не означають виконання всіх DoD або зняття відповідних Windows/BA-гейтів. Див. `docs/P1_EVIDENCE_POINTER_AUDIT.md`.

## Додаткові 12 code/test прив’язок

Наявні synthetic tests для 12 P1/P2-функцій прив’язано до `backlog_audit.py`. Це лише audit/navigation mapping, а не нові реалізації чи бізнес-приймання. Див. `docs/P2_EVIDENCE_POINTER_AUDIT.md`. `releaseApproved=false` залишається незмінним.

## Уточнення перевірок v2.50.14

Кожен `code_locator` і `test_locator` повинен бути або відсутнім (`null`), або непорожнім текстовим значенням. `release_report()` тепер звіряє фактичні кількості рядків із парою код+тест і без code locator зі зведенням `counts` у реєстрі. Якщо хтось видаляє чи змінює вказівник, але не узгоджує зведення, перевірка завершується помилкою. Жодне узгодження лічильників не означає підтвердження реального UAT: `releaseApproved=false` і `humanAcceptance=NOT_RECORDED` залишаються чинними.


## Додатковий source-level audit (без нового релізу)

Після перевірки локальних реалізацій додано три вже існуючі пари code/test locator: `FOCUS-06` (збереження редакторського фокусу / захист від stale detail responses), `QUICK-05` (кандидати швидких передач без зміни sprint/WRITE lane) та `REL-04` (snapshot watcher з обмеженим retry і видимим станом). Це лише покращує навігацію за кодом і синтетичними тестами; повна batch-семантика, справжні браузерні сеанси та Windows/UAT лишаються неперевіреними. Статуси 129 вимог не змінені, `releaseApproved=false`.
